# Безопасность

## Модель доверия

Клиент Roblox считается недоверенным. Эксплойтер может вызвать RemoteEvent вручную, изменить payload, повторять запросы с высокой частотой, подменить локальное время и переместить собственного персонажа. Поэтому визуальная отзывчивость может начинаться на клиенте, но результат всегда подтверждает сервер.

Сервер является единственным источником истины для:

- участия в очереди и составе матча;
- владения мячом и допустимости футбольного действия;
- позиции голевой линии, гола, панны, счёта и таймера;
- победы, поражения, рейтинга, XP и валюты;
- купленной и выбранной косметики;
- выдачи и повторной выдачи награды.

## Проверка сетевого запроса

Каждый `ActionRequest` должен проходить проверки в таком порядке:

1. Отправитель — настоящий `Player`, полученный сервером от RemoteEvent.
2. Payload имеет ожидаемые типы, конечные числа и известное имя действия.
3. Запрос укладывается в общий token bucket и cooldown конкретного действия.
4. Игрок находится в активном матче и привязан к указанной сервером арене.
5. Состояние матча разрешает действие; во время countdown/goal pause/finished оно отклоняется.
6. Персонаж, HumanoidRootPart и мяч существуют.
7. Дистанция до мяча и арены находится в пределах конфигурации, а серверная история движения персонажа не показывает невозможного скачка.
8. Направление нормализовано или безопасно нормализуется сервером; NaN/inf отклоняются.
9. Сила, подъём, скорость и длительность берутся из серверного `Config`, а не из payload.
10. Сервер фиксирует владение и только затем применяет действие.

`QueueRequest` отдельно проверяет, что игрок не находится в матче, не добавлен в очередь повторно и запрашивает только известную операцию.

## Базовые ограничения MVP

`Config.Security` задаёт общий burst/refill для Remote, допустимое отклонение длины горизонтального direction от единицы и максимальный выход персонажа за объём арены. Текущий MVP применяет эти проверки вместе с конечностью/нормализацией направления, состоянием матча, дистанцией до мяча и cooldown действий. `BallService` дополнительно проверяет короткое перемещение и суммарный путь примерно за секунду, учитывает серверный рывок, откатывает невозможный скачок и после трёх недавних нарушений возвращает участника на spawn. Проверка выполняется на Heartbeat и перед действием, а счётчик отражается в `MovementViolationCount`.

Rate limit снижает спам, но не доказывает честность запроса. Проверки контекста, расстояния и состояния обязательны даже для первого запроса.

## Физика и network ownership

- Сервер должен иметь возможность исправить невозможную скорость или положение мяча.
- Перед критическим действием нельзя доверять только позиции, сообщённой клиентом.
- Передача network ownership клиенту требует реальных сетевых тестов и дополнительных sanity checks.
- Мяч, вышедший ниже разрешённой высоты или за границы, возвращается сервером.
- Клиентский эффект удара не означает, что удар был принят.
- Мяч каждой арены сталкивается только с участниками этой арены; spectator/чужие participant groups с ним не сталкиваются. Посторонний внутри занятого `Bounds` дополнительно возвращается в лобби.

## DataStore и награды

- Выдавайте награду через единый серверный путь.
- Связывайте награду с уникальным идентификатором завершённого матча.
- Храните ограниченный список недавно обработанных идентификаторов для защиты от повторов.
- Не делайте бесконечные retry: используйте ограниченное число попыток и backoff.
- В `BindToClose` сохраняйте только уже загруженные профили и учитывайте лимит времени закрытия.
- Не очищайте живые данные при ошибке загрузки и не заменяйте их пустым профилем с последующим сохранением поверх.

MVP атомарно приобретает lease-lock через `UpdateAsync`, выдаёт уникальный lease ID каждому load, требует точный собственный lock для записи, продлевает lease, освобождает его при чистом выходе/shutdown и не допускает два одновременных save одного игрока внутри процесса. Disconnect во время загрузки передаёт освобождение завершившемуся load, а выход во время autosave сериализует финальный release. Shutdown прекращает новые загрузки и ожидает активные load/save в пределах общего budget. Текущие параметры: lease 180 секунд, ожидание занятого локального save до 10 секунд, общий shutdown budget до 25 секунд. Эти механизмы всё равно требуют staging-проверки при быстром rejoin, reconnect/teleport и деградации DataStore.

Ошибка загрузки и неподтверждённый save выставляют `DataSessionFallback`. В таком состоянии `RewardMatch` не применяет награды; published-сервер не допускает игрока в рейтинговую очередь до успешного подтверждённого сохранения. В Studio fallback-матч разрешён специально для разработки, но его прогресс не сохраняется.

Любое завершение из-за disconnect не вызывает путь наград: countdown даёт `Cancelled`, ранняя активная игра — `EarlyForfeit`, поздняя — `Forfeit`. Если disconnect обрабатывается уже после `EndsAt`, сначала вычисляется обычный результат по времени. Это закрывает прямой фарм наград выходами, но не заменяет общую аналитику злоупотреблений.

### Остаточные риски alpha

До соревновательного релиза нужны отдельные adversarial- и latency-тесты следующих границ:

- movement envelope использует эвристические допуски и серверно наблюдаемую client-owned позицию; его нужно настроить против false positive и постепенного speedhack;
- collision groups/eject не проверены с несколькими аренами, respawn, StreamingEnabled и реальными персонажами; при ошибке регистрации групп остаётся только периодический возврат;
- lease/recovery и shutdown требуют staging-тестов с DataStore throttling, быстрым rejoin и остановкой сервера во время load/save;
- нет внешней телеметрии, санкций и более широкого detection для collusion/alt-аккаунтов.

Эти границы не делают клиент источником счёта или валюты, но остаются release blockers для честного рейтингового режима.

## Секреты

В репозитории запрещены:

- GitHub Personal Access Token;
- cookie `.ROBLOSECURITY`;
- Roblox Open Cloud API key;
- пароли, private keys и webhook secrets;
- секреты в примерах, URL, истории Git или снимках экрана.

Для GitHub используйте Git Credential Manager или `gh auth login`. Для CI секреты должны храниться в защищённом secret store платформы и передаваться только нужному шагу. Сейчас проект не требует CI-секретов.

Если секрет когда-либо попал в чат или commit:

1. немедленно отзовите его у провайдера;
2. создайте новый с минимальными правами;
3. проверьте историю Git и журналы;
4. при попадании в историю очистите её специализированным инструментом и считайте старый секрет скомпрометированным даже после удаления строки.

`scripts/validate-project.ps1` ищет несколько высокоуверенных сигнатур, но не гарантирует обнаружение всех секретов.

## Ассеты и плагины

Текущий мир строится процедурно и не содержит внешних ассетов. Перед добавлением free model:

1. проверьте лицензию и автора;
2. разберите модель локально;
3. удалите неизвестные Script/LocalScript/ModuleScript;
4. проверьте require по asset ID, HTTP-запросы и скрытые объекты;
5. перенесите нужную геометрию в контролируемый исходный формат.

Плагины Studio имеют широкие права. Устанавливайте их только из доверенного источника и минимальным набором.
