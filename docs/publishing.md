# Публикация Roblox Experience

## Общий принцип

Сначала публикуйте в закрытый тестовый Experience, затем в отдельный production Experience. Git хранит исходный код, а не секреты и не является автоматическим доказательством готовности Roblox-версии.

## 1. Предрелизная проверка

Из чистой копии нужного commit:

```powershell
./scripts/validate-project.ps1
./scripts/bake-editable-place.ps1 -OutputPath build/Panna-release.rbxlx
```

Обычный `rojo build default.project.json` использует уже запечённый `src/world/PannaDistrict.model.json`; bake-команда перед релизом дополнительно регенерирует его из `WorldBuilder` через чистый `source.project.json`.

Если установлены инструменты:

```powershell
stylua --check src
selene src
```

Затем выполните [тест-план](test-plan.md) в Roblox Studio. Не продолжайте публикацию при ошибках validator, Rojo build, серверного Output или сценариев безопасности.

## 2. Тестовый Experience

1. В Roblox Studio войдите в аккаунт владельца или нужной группы.
2. Создайте отдельный Experience для staging.
3. Откройте собранный `Panna-release.rbxlx` либо синхронизируйте проект Rojo в пустой place.
4. Выберите **File → Publish to Roblox As…** и staging Experience.
5. Оставьте доступ приватным или ограниченным тестовой группой.
6. Включите Studio API Access только при необходимости проверки DataStore именно в staging.
7. Проведите многопользовательский прогон, переподключение и тест реального устройства.

Собранный `.rbxlx` не добавляется в репозиторий. Источником версии остаётся commit SHA.

## 3. Настройки Experience

Перед внешним тестом проверьте:

- название, описание и возрастные рекомендации без заимствования чужого бренда;
- максимальное число игроков с учётом шести одновременных 1v1-матчей (до 12 участников), ожидающих на улице и общей очереди;
- разрешённые устройства;
- локализацию и читаемость интерфейса;
- privacy/permissions для группы разработчиков;
- отсутствие ненужного `HttpService` и сторонних endpoint;
- StreamingEnabled и поведение мира на слабых устройствах;
- DataStore name/schema для выбранного окружения;
- права на все добавленные аудио, изображения, анимации и модели.

На текущем этапе мир создаётся процедурно и не использует внешние ассеты; фактический перечень зафиксирован в [ASSETS.md](../ASSETS.md). Если ресурсы появятся, внесите `asset ID → автор → лицензия → назначение` в реестр до публикации.

## 4. Production-выпуск

1. Зафиксируйте прошедший staging commit и отчёт тестирования.
2. Создайте резервную копию текущего production place/version.
3. Публикуйте тот же проверенный артефакт, не собирая его из незакоммиченных изменений.
4. Сначала оставьте Experience приватным и выполните smoke test двумя аккаунтами.
5. Откройте доступ небольшой аудитории.
6. Наблюдайте server errors, DataStore errors, длительность матчей и отказы Remote.
7. Расширяйте аудиторию только после стабильного окна наблюдения.

Не вводите платные продукты до проверки идемпотентных receipt handlers. Текущая косметическая экономика не должна менять соревновательные характеристики.

## 5. Версии и откат

Для каждого выпуска сохраните:

- commit SHA;
- Roblox place version;
- версию схемы профиля;
- дату и автора публикации;
- ссылку на тест-отчёт;
- краткий changelog.

При критической ошибке:

1. закройте новые входы или сделайте Experience приватным;
2. откатите place к последней подтверждённой версии;
3. не откатывайте схему DataStore вслепую;
4. сохраните логи и воспроизводимый сценарий;
5. исправьте и повторите staging-процесс.

## 6. GitHub и секреты

Публикация из Studio не требует GitHub-токена в проекте. Для push используйте безопасную локальную авторизацию. Roblox Open Cloud, если будет добавлен позже, должен получать ключ из защищённого хранилища CI с минимальными правами и отдельными ключами для staging/production.
